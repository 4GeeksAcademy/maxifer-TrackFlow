# Medición de latencia RAG — 8 de noviembre de 2026

## Método y alcance

Diez consultas reales secuenciales desde el contenedor API de desarrollo,
usando `rag.query()` y la configuración ya cargada. Tres procesos nuevos:
seis consultas (dos rondas), tres consultas con trazas de pila y una con trazas
HTTP. Colección existente de veinte puntos. No se reindexa ni se escriben datos.
Las preguntas públicas del corpus cubren devoluciones, cobertura rural en Aragón
y almacenamiento en Los Ángeles. No se guardan credenciales ni respuestas.

Se instrumentan embedding, consulta Qdrant y llamada generativa sin cambiar el
pipeline de la API. Los tiempos excluyen autenticación, proxy Next, navegador e
importación inicial; no son una medición HTTP de extremo a extremo ni de carga.
Las trazas añaden cierta sobrecarga. Muestra exploratoria pequeña, insuficiente
para un p95 representativo o un compromiso de servicio. No se evalúa aquí la
corrección de las respuestas ni el Recall@3.

## Diagnóstico comprobado

- El coste de búsqueda vectorial es 4–8 ms. Los picos medidos se concentran en
  embeddings remotos y, en menor medida, en generación.
- Las pilas capturadas durante la espera del proceso B muestran HTTPX/OpenAI
  bloqueados leyendo TLS, esperando cabeceras de respuesta de embeddings;
  otra pila muestra espera remota en generación. No distinguen entre cola del
  gateway, proveedor final o problemas de red.
- El pico de B sucede en su segunda pregunta: no basta atribuirlo al arranque.
- La traza HTTP de C confirma timeout efectivo de 45 s por operación HTTP para
  los modelos. En esa consulta rápida no se observaron reintentos. Un timeout
  HTTP por operación no representa un presupuesto total del pipeline.
- En el SDK instalado, `litellm/main.py` lee `kwargs.get("max_retries", None)`
  para embeddings. `litellm/llms/openai/openai.py` aplica
  `max_retries = max_retries or litellm.DEFAULT_MAX_RETRIES`; el valor por defecto
  comprobado es 2. El pipeline pasa `num_retries=0`, por lo que eso no garantiza
  desactivar los reintentos de ese cliente. Incluso `max_retries=0` aislado puede
  caer en el valor por defecto por ese `or`. Es un mecanismo capaz de extender
  las esperas; no se capturaron los intentos HTTP individuales de los dos picos
  y no se les atribuye una cantidad concreta de reintentos.
- El modelo también devuelve tokens de razonamiento: en almacenamiento B,
  243 de 274 tokens de salida declarados fueron de razonamiento, para una
  respuesta de 81 caracteres. Esto justifica probar menor esfuerzo o un modelo
  adecuado a respuestas breves; no demuestra que explique todos los picos.
- Persiste el aviso cliente Qdrant 1.20.0 / servidor 1.15.3. La búsqueda rápida
  observada no lo identifica como causa de esta latencia.

## Soluciones propuestas, por prioridad

1. **Acotar la espera real y controlar reintentos en todas las capas.** Verificar
   el cliente SDK efectivo con una prueba de timeout controlada y contar
   intentos HTTP. Usar una configuración o versión del adaptador que respete
   cero reintentos, o un cliente explícito validado. Añadir un presupuesto total
   de consulta con cancelación efectiva del transporte; devolver un mensaje
   claro al agotarlo. Presupuestos iniciales a experimentar: embedding 5–10 s,
   generación 15–20 s, total 25–30 s. Son propuestas, no valores ya validados.
   Dejar de esperar antes mejora el límite de espera, pero puede aumentar errores
   mientras el proveedor siga lento. Un temporizador que deje un hilo trabajando
   por detrás no basta. Subir otra vez el timeout del proxy no acelera respuestas.
2. **Investigar gateway/proveedor de embeddings.** Correlacionar mediciones e
   identificadores de petición con sus logs para distinguir cola, red y modelo.
   Comparar otra ruta o modelo en la misma muestra. Si cambia el modelo o espacio
   vectorial, usar un índice coherente y repetir la evaluación de recuperación;
   no mezclar vectores ni reemplazar el índice actual durante este diagnóstico.
3. **Cachear embeddings de preguntas repetidas.** Clave con texto y la identidad
   real/versionada del modelo, TTL y tamaño acotados. Evita esa llamada remota en
   aciertos; no ayuda a preguntas nuevas. Para cachear respuestas completas,
   incluir además versión del corpus/índice, prompt, modelo y configuración de
   recuperación, e invalidar al actualizarlos. Las repeticiones actuales sí
   vuelven a llamar al modelo; su aceleración no demuestra una caché propia.
4. **Reducir generación innecesaria.** Ensayar menor razonamiento si el alias lo
   admite y una instrucción de respuesta breve. Ajustar el límite de tokens con
   comprobación de truncamiento y de las condiciones comerciales del corpus.
   Comparar calidad y latencia antes de escoger otro modelo. El máximo de tokens
   por sí solo no corrige las esperas del embedding.
5. **Streaming y observabilidad permanente.** Mostrar tokens conforme llegan y
   medir tiempo al primer token, total, etapas, errores e intentos con logs sin
   datos sensibles. Streaming permite leer antes cuando empieza la generación;
   no elimina el bloqueo previo del embedding. Medir después API directa y
   proxy autenticado para completar el presupuesto de extremo a extremo.

En la medición inicial no se aplicaron optimizaciones funcionales ni se cambió
entorno, modelos, infraestructura o datos persistentes. La implementación
posterior se documenta más abajo. No se ha realizado commit ni push.

## Reproducción

```powershell
docker compose exec -T services python -m scripts.benchmark_rag --rounds 2
docker compose exec -T services python -m scripts.benchmark_rag --rounds 1 --trace-slow
docker compose exec -T services python -m scripts.benchmark_rag --rounds 1 --question returns --trace-http
```

Cada ejecución realiza llamadas facturables a los modelos configurados. El script
emite JSONL y solo consulta la colección existente. `--trace-slow` imprime pilas
cada quince segundos: la palabra `Timeout` en esas trazas es el disparador del
diagnóstico, no una excepción de timeout de la llamada de modelo.

## Implementación y segunda medición

Se implementan transporte HTTPX asíncrono al mismo gateway y aliases, sin
reintentos locales; presupuesto total de consulta de 30 s, con etapas de
embedding/búsqueda/generación de 10/5/20 s reducidas al tiempo restante; y cachés
por proceso de 256 entradas, embeddings 15 min y respuestas 5 min. La búsqueda
siempre comprueba el índice actual y la clave de respuesta incluye el contexto
recuperado, el prompt y la configuración. No se cambian modelos, prompt ni
parámetros de generación. El endpoint sigue devolviendo errores HTTP 503 con
un mensaje de espera agotada y sugerencia de reintentar.

La revisión automática rechazó inicialmente las llamadas reales por el envío de
preguntas y fragmentos al gateway. Tras autorización explícita del desarrollador,
se ejecutaron exactamente seis consultas al destino configurado, sin reindexar.
Las mediciones son del pipeline en otro proceso, no de HTTP autenticado completo.

**No debe presentarse esta tanda como seis respuestas más rápidas:** hubo dos
respuestas y cuatro cancelaciones al llegar al límite de diez segundos. Confirma
que la espera queda acotada y también que ese límite puede ser restrictivo para
el proveedor actual. Cambiarlo sería un equilibrio entre tasa de respuesta y
espera permitida, sin eliminar la latencia remota.

No hubo aciertos de caché de respuestas en esta tanda: las primeras cuatro
consultas fallaron antes de obtener un embedding; las dos últimas fueron los
primeros éxitos de sus preguntas. La prueba local de repetición comprueba que
una segunda consulta evita ambos modelos y sigue consultando Qdrant; también
comprueba invalidación por cambios del contexto/modelos/credenciales. No se
atribuye a esa prueba una latencia remota observada.

Las pruebas cubren TTL, expulsión por capacidad, aislamiento de valores mutables,
errores y truncamientos sin caché, orden de vectores en lotes, un intento HTTP
ante 429/500/503, presupuesto restante y cierre de una conexión TCP real local
al cancelar. Las pruebas del endpoint comprueban autenticación y el mensaje 503.
La API de desarrollo se reinicia para cargar el código; su salud HTTP devuelve 200.
